# Omnizen integration — draft PR description

> Branch: `feat/omnizen-integration` (off `main`)
> Target: `main` of `anchorblock/open-webui` (our fork)
> **Not** to be opened against upstream `open-webui/open-webui`.

## Summary

This branch turns this fork into the chat surface for Omnizen
(https://chat.omnizen.ai). Three changes, all additive:

1. **Per-user Omnizen API key passthrough**
   — New module `backend/open_webui/integrations/omnizen.py` that
   resolves the per-user stored API key (the OpenWebUI `api_key`
   table, already managed via the existing /account UI) and uses it
   for upstream chat-completion calls to `https://api.omnizen.ai/v1`.
   Wired in via a 1-line edit in `routers/openai.py` immediately
   after the global key is read. Falls back to the global key on
   missing-key / DB error.

2. **CI for the Omnizen-branded image**
   — New workflow `.github/workflows/omnizen-build.yml` that, on
   push to `main`, builds and pushes
   `ghcr.io/anchorblock/open-webui-omnizen:latest` (plus
   `:sha-XXXXXXX`). Does not touch upstream's existing
   `docker-build.yaml` so future merges stay clean.

3. **Branding asset placeholder**
   — `static/omnizen-favicon.png` (clone of upstream `favicon.png`
   for now; real Omnizen mark will land in a follow-up). Branding
   text comes through the `WEBUI_NAME=Omnizen Chat` env that's
   already set in `omnizen-ai/docker-compose.web.yml`.

## What this PR does **not** change

- No edits to upstream CI files (`docker-build.yaml`,
  `build-release.yml`, etc.)
- No edits to PR templates / CLA / contribution docs
- No new top-level config keys, no schema migrations
- No changes to existing auth flows; trusted-header auth is configured
  at runtime via env (`WEBUI_AUTH_TRUSTED_EMAIL_HEADER`) — that env
  toggle is set on the deployment side, not in this repo.

## Testing notes

- `from open_webui.integrations.omnizen import resolve_user_api_key`
  imports cleanly (no circular import — the `Users` import is lazy
  inside the function).
- A user with no stored key receives the global key (preserves
  admin-test behaviour).
- A user with a stored key prefixed `om_` is logged at debug, key is
  used unchanged.
- A DB exception during lookup logs a warning and returns the
  fallback key (fail-open).
- End-to-end on staging:
  1. Sign in at `https://omnizen.ai`
  2. Click "Chat" in the marketing nav
  3. Lands at `https://chat.omnizen.ai`, auto-provisioned via
     trusted-header auth
  4. Open `/account` in OpenWebUI, paste an Omnizen API key
  5. Send a message; verify spend appears in
     `https://omnizen.ai/dashboard/analytics` against the right
     account (not against the LiteLLM master key)
